# T-III — the LLM pipeline, and how its output is checked

This directory answers one question: **can an LLM, shown a video of a specific
failure, write a reward function and an episode sampler good enough to train a
residual on — and how would you know?**

The deliverable is the assignment's:

> Implement a pipeline in which an LLM takes as input an mp4 video of a
> particular failure configuration (from T-II) and generates: (a) a dense reward
> function as executable Python operating on ManiSkill state that incentivizes
> recovery from/avoidance of that failure; (b) an episode-configuration sampler
> that biases initial conditions toward the failure regime. Document the
> prompt(s) you used and discuss why the generated reward function would be
> useful to improve performance. Also discuss failure modes of the LLM itself
> (e.g. reward hacking, mis-specified terms) and manual effort to elicit desired
> results.

Read this file top to bottom and you will know what the model is given, what it
must produce, and — the part that took the most work — what has to be true
before its output is allowed anywhere near a GPU.

---

## 0. The claim this directory has to support

"The LLM wrote a reward function" is not a result. Anything can write a reward
function; the code will run, the numbers will be finite, and the rationale will
read well. **The question is whether training on it would help**, and the honest
answer to that is not available from reading the code.

So the substance here is not the API call. It is the definition of what
"acceptable" means, made precise enough to be checked mechanically, and a gate
that applies it. The API call is one file and 250 lines. The checking is five.

The operational form of "would help" used throughout:

> A useful reward **ranks real episodes by their real outcome, at the stage the
> failure mode actually breaks at.**

That sentence is the thesis. Everything in §3 is machinery for testing it.

## 1. What the model is given

Eureka-style: the environment's own source, a natural-language description of
the failure, and the video. Deliberately **not** T-II's numeric table.

| block | file | why |
|---|---|---|
| role and output discipline | `prompts/system.md` | the `system` parameter |
| the environment, in full | `env_source/stack_cube.py` + `prompts/env_source.md` | the model should read the success criterion and the existing reward, not be told about them |
| the allowed API surface | rendered from `spec.py` | so it is byte-identical to what the checker enforces |
| how generated rewards go wrong | `prompts/hacking.md` | **the tuning knob** |
| the failure, in prose | `prompts/failure_gap.md`, `failure_farb.md` | written by hand from the T-II measurement |
| the frames | `frames/*.jpg` + `prompts/frames.md` | the assignment's actual input |
| the task and the contract | `prompts/task.md` + `spec.contract_markdown()` | |

Four decisions worth defending.

**No numbers by default.** `prompts/stats.md` holds T-II's measured rates and is
included only under `WITH_STATS=1`. The default withholds it so that what the
model infers about the mechanism comes from the video and the prose. Running
both arms and diffing the generated rewards is the cleanest available measure of
how much the video is actually contributing, and which arm produced an artifact
is recorded in its manifest.

**The prompt is files, not string literals.** Tuning it is `git diff
t3/prompts/hacking.md`, which is exactly what the "manual effort to elicit
desired results" deliverable needs to be able to show. No prompt text lives in
Python.

**Two sections are rendered from `spec.py`, not written by hand.** The contract
and the API surface are generated by the same module the checker reads, spliced
in at `{{CONTRACT}}` and `{{API_SURFACE}}`. A rule cannot be tightened in the
checker without the model being told about it, and `test_spec.py` asserts every
enforced name appears in the rendered text.

**The environment source is a committed snapshot with a run-time hash gate.**
A live read out of `$MANISKILL_REPO` cannot drift from the installed version but
makes an old run's prompt unreproducible once the pod is gone, and invisible to
`git diff`. A snapshot is reproducible and reviewable but rots. `assemble.py`
re-hashes the installed copy on every build and refuses to proceed if they
differ — both properties for the price of one comparison, the same move
`t2/harness.py` makes with `ckpt_sha256`.

### Frames

`assemble.py` shells out to the `ffmpeg` binary rather than importing anything,
so frame extraction adds no Python dependency. Two strategies: `uniform` (evenly
spaced, first and last pinned — the first frame *is* the initial configuration,
which is what a T-II failure mode is) and `diverse` (greedy farthest-point over
32×32 grayscale thumbnails compared in pure Python). `diverse` exists because
every episode runs the full 200 steps under `ignore_terminations=True`, so a
uniform sample spends most of its frames on a motionless tail.

## 2. The contract — `spec.py`

Two modules, two functions, one constant:

```python
# reward.py
REWARD_MAX = 8.0
def compute_reward(env, obs, action, info): ...   # -> (num_envs,), in [0, REWARD_MAX]

# sampler.py
def sample_cube_poses(b, device): ...             # -> {cubeA_xyz, cubeA_quat, cubeB_xyz, cubeB_quat}
```

**Parameter names are checked exactly and in order.** A generation emitting
`compute_reward(env, action, obs, info)` parses, imports, runs, and computes the
reward from the wrong tensor. That has to be a load error, not a debugging
session.

**The sampler takes `(b, device)` and never touches `env`.** That is the single
best structural decision here: 4,096 draws can be checked in a second, on a
laptop, with torch and `t2/geometry.py` and nothing else. It also removes the
"sampler reaches into the simulator" hack surface by construction rather than by
check. Everything a sampler could legitimately want from `env` — the cube size,
the table region, the arm's base — is a constant, and constants belong in the
prompt.

**The reward takes `env` explicitly** rather than being a bound method, so the
validator can call it standalone without constructing the env subclass.

**Randomness must be `torch`.** `_initialize_episode` runs inside a seeded
`torch.random` fork, so `reset(seed=s)` stays deterministic only if the sampler
draws from torch. A `random.uniform` would pass every other check and silently
destroy the seed addressing that every evaluation in this project depends on.
This is the most important static rule and it has its own fixture.

### Integration — `env_t3.py`

`@register_env("StackCube-T3-v1")`, subclassing `StackCubeEnv`. ManiSkill has no
hook for a custom reward; subclass-and-register is the supported path.
`_initialize_episode` calls `super()` **first** — keeping
`TableSceneBuilder.initialize`'s robot qpos, table pose and open gripper — then
overrides only the two cube poses.

Two environment variables:

```
T3_RUN      the generation directory holding reward.py and sampler.py
T3_SAMPLER  1 (default) biased sampling; 0 the environment's own
```

**`T3_SAMPLER=0` is load-bearing, not a convenience.** With the biased sampler
on, `reset(seed=s)` no longer produces the state `t2/results/seeds.csv` records
for `s` — by design — and any measurement that has to reproduce a T-II episode
is then over a different population. So it is forced off in `align.py`, recorded
in the manifest, and **checked by the gate**. It stays on for T-IV *training*
only.

## 3. The five layers, and what each one proves

| layer | proves | cost | laptop? |
|---|---|---|---|
| **A** static | the artifact is code of the right shape and reads nothing outside the contract | 0.2 s | yes |
| **B** runtime | `(num_envs,)`, finite, in range, **pure**, and **does not mutate the simulator** | ~2 min | no |
| **C** probes | hand-built degenerate states score below a completed stack | in B's run | decision only |
| **D** alignment | **the reward ranks real episodes by their real outcome, at the failing stage** | ~8 min | decision only |
| **E** sampler | the biased distribution is concentrated, legal, varied, and reproducible | ~1 min | E1 yes |

Everything that needs a simulator **writes numbers to a file**; `verify.py` reads
those files and decides. That split is why `test_verify.py` can fabricate a
complete pass, corrupt it twenty-one ways, and confirm each is caught — on a
laptop, in two seconds, with no simulator and no API key.

### Layer A — `loader.py`

AST walk, then `exec` into a namespace with a whitelisting `__import__`.
Import whitelist, no `while`, no classes or decorators, no dunder attributes, no
`.item()`/`.cpu()` (a per-step GPU sync at PPO's batch width), no
`.set_pose`/`set_state` (mutation), `env.<chain>` resolved against the allowed
surface, `info[...]` keys checked as literals, required signatures, `REWARD_MAX`
a positive literal.

**It is not a security sandbox, and the docstring says so.** The code came from
our own prompt and is committed and reviewed. Layer A catches accidents and
mis-specification cheaply. A false claim of containment would be worse than the
honest limit.

### Layer B — shape, purity, no mutation

Two checks here are worth more than they look. **Purity** — call the reward
twice on an unchanged state, require bitwise equality — catches a `torch.rand_like`
buried in a shaping term, which would make every advantage estimate noisy in a
way no amount of training averages out. **No mutation** — snapshot
`env.get_state()` around the call — catches a reward that moves cubeA onto cubeB
itself and then collects the bonus for cubeA being on cubeB. Layer A bans
`.set_pose` by name; this does not depend on having thought of the right name.

### Layer C — the probes, and the one that cannot be injected

Rollouts only ever show states the base policy produces. The policy never puts
cubeB on top of cubeA, so **no number of rollouts reveals a reward with the goal
arguments swapped**; it never drops a cube through the table, so nothing reveals
a reward that measures only horizontal distance. Those are exactly the
mis-specifications an LLM produces, and a hand-built state is the only way to
find them.

Nine states, and two 24-point sweeps walking cubeA away from the goal
vertically and horizontally. The sweeps carry two assertions, and the second one
earns its keep: the reward must not *rise*, and it must actually **vary** — a
reward that ignores height is perfectly monotone along the z sweep because it is
constant along it.

**`P7_held` cannot be injected, and finding that out cost an afternoon.**
`Panda.is_grasping` reads pairwise *contact forces* from the last physics step.
After a reset plus `set_pose` with no stepping there are no contacts, so
`is_cubeA_grasped` is **False in every hand-injected state** — and "cubeA held
above cubeB and never released", the canonical consequence of a grasp-heavy
reward, is precisely a grasped state. So `P7_held` is restored from a state dict
captured during a real rollout (`probes.py --make-fixture`), stepped twice with
the gripper closing, and the flag is asserted to have come back. `verify.py`
fails if that assertion did not hold, rather than scoring a mislabelled state.

### Layer D — alignment, the centrepiece

100 real episodes of the frozen base policy, on the failure region's **own T-II
evaluation seeds**, through `StackCube-T3-v1` at `reward_mode="dense"`.
Cumulative generated reward arrives free: `CPUGymWrapper(record_metrics=True)`
already sums whatever reward the env returns into `info["episode"]["return"]`,
beside `success_once`. The only code change T-III makes to `t2/` is a
`reward_mode` keyword on `harness.build_agent`, defaulting to `"sparse"` so
every existing T-II number is on an identical path.

What the gate then applies:

- **AUC of cumulative reward against `success_once` ≥ 0.75**, with **z ≥ 3.0**
  against the null, and a mean gap ≥ 10% of the observed range. Significant
  *and* a real size.
- **Mean return must rise with the stage reached**, by a margin: `grasped, not
  placed` < `placed, not success` < `success`. **This is the binding stage
  test.**
- The real policy must beat a `jitter` arm (wanders near the cubes, completes
  nothing — the "farm the shaping term" policy) and a `zero` arm, by a *ratio*,
  so the threshold survives whatever scale the model chose.
- **The join back onto T-II.** Every logged initial state must match
  `mode_<tag>_seed1.csv` on all six pose columns to 1e-5. Free, and it is the
  structural proof that the subclass did not perturb the distribution T-IV will
  be scored on.

#### A correction worth recording: the conditional AUC is *not* the binding test

The design intent was that the load-bearing check would be a stage-conditional
AUC — for `gap`, `AUC(return ; ever_placed | ever_grasped)` — on the reasoning
that a grasp-farming reward scores well unconditionally and at chance
conditionally. The arithmetic says otherwise, and it was caught while writing
the gate's own test rather than by reasoning.

Successful episodes are a **subset** of placed ones. So if a reward ranks
success at the top — which the unconditional check already requires — those
episodes win every conditional pair for free. At T-II's measured stage rates
(96 grasped, 66 placed, 52 successful of 100) the floor is

```
52 × 30 / (66 × 30) = 0.788
```

already above the 0.70 threshold. **A reward that pays nothing at all for
placement would pass it**, provided it pays for success.

The conditional AUC is kept and reported — it is a graded number and it does
catch gross failure — but the check the gate leans on is the stage-margin
ladder above, which a grasp-farming reward inverts at its first step however
large its success bonus. `test_verify.py`'s `_grasp_farm` corruption is exactly
that reward, and it is the stage check that catches it.

This is in `spec.ALIGN_STAGE_GAP_FRAC`'s comment as well, because it is the kind
of thing that gets silently "simplified" back.

#### Power

Recomputed by `test_spec.py` on every run, so the numbers below cannot go stale:

| test | n₁/n₀ | SE_null | z at the threshold |
|---|---|---|---|
| unconditional, n=100 | 52/48 | 0.058 | **4.3** |
| unconditional, n=60 | 31/29 | 0.075 | 3.3 |
| unconditional, n=30 | 16/14 | 0.107 | 2.3 — fails the z ≥ 3 bar |

Hence 100 episodes, and a gate that refuses fewer than 60. **This test detects a
badly misaligned reward, not a marginally better one**, and the report says so.

#### The calibration arm

`bash t3/run.sh calibrate` runs the identical battery on
`fixtures/stock_reward.py`, a faithful transcription of ManiSkill's own 8-stage
`compute_dense_reward`. Without it every AUC is uncalibrated. With it, "the
generated reward separates outcomes at 0.82 against the stock reward's 0.79 on
the same 100 episodes" is a result — **and so is the other outcome.** CLAUDE.md
already notes that T-III's reward "has a real baseline to be compared against
rather than invented in a vacuum"; this is where that gets cashed.

### Layer E — the sampler

4,096 draws, called directly, no simulator. Legality (unit quaternions about z
only, cubes on the table, separation ≥ 58.6 mm — the environment's own
rejection floor — inside the nominal support, inside the arm's reach), then:

- **hit rate ≥ 0.60**, and **enrichment ≥ 10×** over the nominal rate, which is
  *computed at run time* from the committed 25,000-seed index rather than
  hardcoded. Measured there: `gap` 1171/25000 = **4.68%**, `farb` 843/25000 =
  **3.37%**.
- **non-degeneracy** — per-coordinate SD, `face_gap` SD, yaw-bin coverage,
  distinct-pose fraction. A sampler collapsed onto one configuration hits the
  region 100% of the time and produces a residual that overfits it.
- **coverage of the T-IV scoring set** — ≥ 80% of the fixed T-II evaluation
  episodes must have a draw within 20 mm on `face_gap`, `dist_A` and `dist_B`.
  A sampler can satisfy the region predicate while concentrating in one corner
  of it; that is precisely the failure that makes T-IV's number disappointing,
  and it costs nothing to check.
- **determinism** — same torch seed, same draws, twice; and again through the
  real environment. The one check that catches a sampler drawing from `numpy`.

## 4. Checking the checker

Three self-tests, all on the bare system interpreter, ~3 s total.

| | proves | how |
|---|---|---|
| `test_spec.py` | the contract, the prompt and the statistics agree | every enforced name appears in the rendered prompt; AUC against hand-computed cases and 200 random brute-force cross-checks; the power table recomputed; the base rates re-derived from `t2/results/seeds.csv` |
| `test_loader.py` | **layer A catches things** | 35 committed fixtures — 17 that must be rejected *naming the right reason*, 18 that must pass |
| `test_verify.py` | **the gate catches things** | fabricate a valid pass at T-II's real stage rates, corrupt it 21 ways, confirm each is caught for the right reason |

The fixtures are the answer to "how do you test a validator whose input is
generated": **commit the bad generations.** `fixtures/` holds one file per real
mistake — `bad_argorder.py`, `bad_nondeterministic.py`, `hack_grasp_only.py`,
`hack_inverted.py`, `bad_sampler_collapsed.py`, and so on — each with a
docstring naming the failure it simulates. `good_reward.py`, `good_sampler.py`
and `stock_reward.py` are the positive controls, because a gate nobody has seen
accept anything is a gate that might reject everything.

## 5. Reproducing it

```bash
# 0. the input: a clip of a real failure, from T-II. mp4s are gitignored.
SEEDS=<a seed from t2/results/mode_gap_seed1.csv> WANT=fail bash t2/run.sh videos

# 1. everything
source /workspace/ripl/env.sh
export ANTHROPIC_API_KEY=...          # or $RIPL_ROOT/anthropic.env, chmod 600
MODE=gap VIDEO=~/clip.mp4 bash t3/run.sh all
```

| stage | needs | cost |
|---|---|---|
| `test` | nothing | 3 s |
| `frames` `prompt` | ffmpeg | 5 s |
| `generate` | `anthropic`, a key | ~2 min |
| `lint` | nothing | 0.2 s |
| `probes` `sampler` | ManiSkill | ~3 min |
| `smoke` | + the checkpoint | ~1 min |
| `align` `calibrate` | + the checkpoint | ~16 min |
| `verify` | nothing | 1 s |

**Nothing is reportable, and nothing goes into T-IV, until `verify` exits 0.**

On the laptop, without a pod: `test`, `frames`, `prompt`, `generate`, `lint`,
`verify` and `report` all run. See CLAUDE.md's nix-shell note — `ffmpeg` and
`anthropic` (0.109.1 in nixpkgs, which is why the API call uses tool use rather
than the newer structured-output parameter) both come from `nix-shell -p`.

## 7. For the report

- **The prompts** are committed twice on purpose: the editable sources under
  `prompts/` (small, diffable — the thing you tune) and the exact assembled
  `prompt.txt` per run (the thing the model saw — they differ, because the
  contract and the environment source are spliced in). The frames are committed
  beside them.
- **Why the reward would help.** Two arguments, and they should be labelled as
  different kinds. *A priori*: the built-in reward is a task-completion reward,
  uniform over the initial-state distribution, and its gradient is flat exactly
  where the base policy is already competent; a mode-targeted reward adds the
  term the failure needs — clearance during the descent for `gap`, settling and
  release quality for `farb`. *Empirical*: the stage-margin ladder and the AUC,
  against the stock reward's on the same episodes. Only the second is evidence.
- **LLM failure modes.** The fixture list is the taxonomy; the report says which
  ones the actual generations exhibited, which layer caught each, and — most
  interestingly — the near-misses that passed A, B and C and failed only at D.
  Those are the ones no prompt can prevent and only a rollout finds, which is
  this directory's central claim.
- **Manual effort.** `git log t3/prompts/` is the record: each tuning pass, what
  failed before it and what passed after. Plus generations attempted against
  generations accepted, and the token and wall-clock spend from the manifests.
  And the honest headline: **most of the effort here went into the validator,
  not the prompt.** That is a finding about LLM-generated rewards, not an
  apology for the pipeline.

The debugging narrative goes in `notes/t3-llm-reward.md`, as with T-II.
CLAUDE.md is explicit that those are deliverables, not overhead.
