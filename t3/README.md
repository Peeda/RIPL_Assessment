# T-III — the LLM pipeline, and how its output is checked

This directory answers one question: **can an LLM, shown a video of a specific
failure, write a reward function and an episode sampler good enough to train a
residual on — and how would you know?**

The deliverable is the assignment's:

> Implement a pipeline in which an LLM takes as input an mp4 video of a
> particular failure configuration (from T-II) and generates: (a) a dense reward
> function as executable Python operating on ManiSkill state that incentivizes
> recovery from/avoidance of that failure; (b) an episode-configuration sampler
> that biases initial conditions toward the failure regime. Document the
> prompt(s) you used and discuss why the generated reward function would be
> useful to improve performance. Also discuss failure modes of the LLM itself
> (e.g. reward hacking, mis-specified terms) and manual effort to elicit desired
> results.

---

## 0. The claim, and the size of the check

"The LLM wrote a reward function" is not a result. Anything can write a reward
function; the code will run, the numbers will be finite, and the rationale will
read well. **The question is whether training on it would help**, and that
answer is not available from reading the code.

The operational form used throughout:

> A useful reward **ranks real episodes by their real outcome, at the stage the
> failure mode actually breaks at.**

**This harness used to be a gate.** Five validation layers, a 500-line checker
that exited non-zero, a nine-state probe battery, and a suite that corrupted a
fabricated pass twenty-one ways to prove the checker caught each. It was
defensible and it was the wrong instrument: a reward scoring 0.72 where the
threshold said 0.75 is a thing to write a sentence about, not a thing to block
T-IV on, and every refusal costs a regeneration cycle to learn what the number
already said.

So it now **measures and prints**. `check.py` writes numbers to files;
`summary.py` reads them, marks each OK or WARN, and **exits 0**. The only
refusal left is an artifact that will not load, which is not a judgement call.
A WARN is a finding — put it in the report. §4 is honest about what that costs.

## 1. What the model is given

Eureka-style: the environment's own source, a natural-language description of
the failure, and the video. Deliberately **not** T-II's numeric table.

| block | file | why |
|---|---|---|
| role and output discipline | `prompts/system.md` | the `system` parameter |
| the environment, in full | `env_source/stack_cube.py` + `prompts/env_source.md` | the model should read the success criterion and the existing reward, not be told about them |
| the API surface | rendered from `spec.py` | byte-identical to what the checker reads |
| how generated rewards go wrong | `prompts/hacking.md` | **the tuning knob** |
| the failure, in prose | `prompts/failure_gap.md`, `failure_farb.md` | written by hand from the T-II measurement |
| the frames | `frames/*.jpg` + `prompts/frames.md` | the assignment's actual input |
| the task and the contract | `prompts/task.md` + `spec.contract_markdown()` | |

Four decisions worth defending.

**No numbers by default.** `prompts/stats.md` holds T-II's measured rates and is
included only under `WITH_STATS=1`. The default withholds it so that what the
model infers about the mechanism comes from the video and the prose. Running
both arms and diffing the generated rewards is the cleanest available measure of
how much the video actually contributes, and which arm produced an artifact is
recorded in its manifest.

**The prompt is files, not string literals.** Tuning it is `git diff
t3/prompts/hacking.md`, which is exactly what the "manual effort to elicit
desired results" deliverable has to be able to show. No prompt text lives in
Python.

**Two sections are rendered from `spec.py`, not written by hand.** The contract
and the API surface are generated by the same module the checker reads, spliced
in at `{{CONTRACT}}` and `{{API_SURFACE}}`. A rule cannot be tightened in the
checker without the model being told about it.

**The environment source is a committed snapshot with a run-time hash check.**
A live read out of `$MANISKILL_REPO` cannot drift from the installed version but
makes an old run's prompt unreproducible once the pod is gone, and invisible to
`git diff`. A snapshot is reproducible and reviewable but rots. `assemble.py`
re-hashes the installed copy on every build, warns when they differ, and stamps
the drift into the manifest — the same move `t2/harness.py` makes with
`ckpt_sha256`.

**Frames** come from the `ffmpeg` binary rather than a Python package, so
extraction adds no dependency. Evenly spaced with the first and last pinned: the
first frame *is* the initial configuration, which is what a T-II failure mode
actually is, and the last is the outcome.

## 2. The contract — `spec.py`

Two modules, two functions, one constant:

```python
# reward.py
REWARD_MAX = 8.0
def compute_reward(env, obs, action, info): ...   # -> (num_envs,), in [0, REWARD_MAX]

# sampler.py
def sample_cube_poses(b, device): ...             # -> {cubeA_xyz, cubeA_quat, cubeB_xyz, cubeB_quat}
```

**Parameter names are checked exactly and in order.** A generation emitting
`compute_reward(env, action, obs, info)` parses, imports, runs, and computes the
reward from the wrong tensor. That has to be a load error, not a debugging
session.

**The sampler takes `(b, device)` and never touches `env`.** The best structural
decision here: 4,096 draws can be checked in a second, on a laptop, with torch
and `t2/geometry.py` and nothing else. It also removes the "sampler reaches into
the simulator" hack surface by construction rather than by check. Everything a
sampler could legitimately want from `env` is a constant, and constants belong
in the prompt.

**Randomness must be `torch`.** `sapien_env.py:951` seeds torch's global
generator and *nothing else* before calling `_initialize_episode`:

```python
with torch.random.fork_rng():
    torch.manual_seed(self._episode_seed[0])
    self._initialize_episode(env_idx, options)
```

A sampler drawing from `numpy.random` or `random` draws from a stream
`reset(seed=s)` does not control. Scope it honestly — the generated sampler only
runs under `T3_SAMPLER=1`, so T-II's seed index and T-IV's before/after scoring
are safe; what breaks is **T-IV's training distribution**, which stops being
reproducible run to run. The nasty part is that the obvious test passes, because
a fresh process starts numpy from the same place too. What catches it is
`check.py sampler`'s determinism check: draw twice under one `torch.manual_seed`
and compare. It cannot use ManiSkill's own seeded `_batched_episode_rng`
either — the contract gives it no `env`.

### Integration — `env_t3.py`

`@register_env("StackCube-T3-v1")`, subclassing `StackCubeEnv`. ManiSkill has no
hook for a custom reward; subclass-and-register is the supported path.
`_initialize_episode` calls `super()` **first** — keeping
`TableSceneBuilder.initialize`'s robot qpos, table pose and open gripper — then
overrides only the two cube poses.

```
T3_RUN      the generation directory holding reward.py and sampler.py
T3_SAMPLER  1 (default) biased sampling; 0 the environment's own
```

**`T3_SAMPLER=0` is load-bearing, not a convenience.** With the biased sampler
on, `reset(seed=s)` no longer produces the state `t2/results/seeds.csv` records
for `s` — by design — and any measurement that has to reproduce a T-II episode
is then over a different population. `check.py align` forces it off, records it
in the manifest, and `summary.py` warns loudly if a pass got it wrong. It stays
on for T-IV *training* only.

## 3. What is checked

Errors refuse; warnings print. Something is an **error** only when it makes the
artifact unusable or silently wrong.

### `loader.py` — the static check, 0.2 s, no simulator

Walks the syntax tree before the module is imported. **Errors:** does not parse;
a forbidden import; a missing required function or wrong parameter names/order;
a missing or non-literal `REWARD_MAX`; a `while` loop (rejection sampling must
be a bounded `for`, or a pathological region hangs every reset in training); an
attribute that mutates the simulator (`set_pose`, `set_state`, `step`, `reset`);
`eval`/`exec`/`open`/`getattr`. **Warnings:** `.item()`/`.cpu()`/`.numpy()`,
which force a GPU sync per step; reading an `env` attribute or an `info` key
outside the documented surface.

Not a security sandbox, and this is worth saying plainly: the code came from our
own prompt, is committed, and is read by eye before it trains anything. This
catches accidents and mis-specification somewhere cheaper than a rollout.
Claiming containment would be false, and a false claim is worse than an honest
limit.

### `check.py sampler` — deliverable (b), ~1 min

4,096 draws, straight from `sample_cube_poses`, converted through
`t2/geometry.py`. Measures: physical validity (unit z-only quaternions, cubes on
the table, separation above the environment's own 58.6 mm rejection floor,
inside the nominal support, inside the arm's reach); the **hit rate** against
`geometry.MODES[tag]` and its **enrichment** over the base rate computed at run
time from the committed seed index; the per-coordinate spread; and determinism
under a fixed torch seed.

The spread matters more than it looks. A sampler that returns one configuration
hits the region 100% of the time and teaches a residual a single initial state.

### `check.py reward` — well-formedness, ~1 min

Two seeds, 20 random-action steps. Shape `(num_envs,)`, floating, finite, right
device, inside `[0, REWARD_MAX]`, **pure** (call twice on an unchanged state,
require bitwise equality) and **non-mutating** (`env.get_state()` snapshot before
and after).

The last two earn their keep. A single `torch.rand_like` buried in a shaping
term makes every advantage estimate noisy in a way no amount of training averages
out, and nothing else here would notice. And the nastiest hack available is a
reward that moves cubeA onto cubeB itself and then collects the bonus — the
static check bans `.set_pose` by name, the snapshot does not depend on having
thought of the right method name.

Shape and finiteness stop the pipeline; they would crash or silently corrupt
PPO. Bounds and purity are warnings.

### `check.py align` — deliverable (a), ~8 min. The one that matters.

100 real episodes of the frozen base policy, on the failure region's own initial
states, with the generated reward installed as the environment's actual reward.
Then: did the episodes that succeeded accumulate more of it than the ones that
failed?

A reward that cannot separate observed success from observed failure **on the
policy we already have** will not shape a residual toward success, whatever its
rationale said. The seeds are T-II's own — the `seed` column of
`mode_<tag>_seed1.csv`, the fixed block T-IV is scored on — so this measurement
and the eventual before/after are the same initial states.

Reported: the AUC of cumulative reward as a classifier of `success_once`, its z
against the null, and the **stage ladder** — mean return for "grasped, not
placed" < "placed, not success" < "success".

#### The stage ladder is the test, and a conditional AUC is not

The design intent was that a stage-conditional AUC — `AUC(return ; ever_placed |
ever_grasped)` for `gap` — would catch a reward that farms reaching and grasping.
The arithmetic says otherwise, and this was found by writing the check's own test
rather than by reasoning.

Successful episodes are a **subset** of placed ones. So a reward that ranks
success at the top — which the unconditional check already requires — wins every
conditional pair for free. At T-II's measured stage rates for `gap` (96 grasped,
66 placed, 52 successful of 100) the floor is

```
52 × 30 / (66 × 30) = 0.788
```

already above the 0.70 it was gated at. **A reward paying nothing at all for
placement would have passed it.**

What does catch that reward is requiring the mean return to *rise* from stage to
stage with a real margin. A grasp-farming reward inverts the first step however
large its success bonus. Verified against a fabricated one: unconditional AUC
1.000, stage ladder `grasped=70.0 < placed=60.2 < success=94.6` — flagged. This
is also in `spec.ALIGN_STAGE_GAP_FRAC`'s comment, because it is the kind of thing
that gets silently "simplified" back.

#### Power, and the calibration arm

At n=100 with roughly 52/48 the null SE of the AUC is 0.058, so the 0.75
threshold sits 4.3 SDs from chance. **This detects a badly misaligned reward,
not a marginally better one**, and the report should say so.

`bash t3/run.sh calibrate` runs the identical battery on
`fixtures/stock_reward.py`, a faithful transcription of ManiSkill's own 8-stage
`compute_dense_reward`, through the identical code path. Without it every AUC is
uncalibrated. With it, "the generated reward separates outcomes at 0.82 against
the stock reward's 0.79 on the same 100 episodes" is a result — **and so is the
other outcome.**

## 4. What is NOT checked, and what that costs

The deleted probe battery caught real classes of mistake. Three now have no
automated substitute, and pretending otherwise would be worse than the gap.

1. **Swapped goal arguments.** A reward that pays for getting cubeB onto cubeA.
   The base policy never produces that state, so no number of rollouts exposes
   it. **Nothing catches this** — only reading `reward.py`.
2. **"Hold it up forever."** The canonical mis-specification: reward the
   placement, forget that StackCube's success criterion explicitly requires the
   release. *Partially* covered — the ladder's `placed < success` step drops if
   the reward pays for holding — but not directly. It cannot be probed cheaply
   anyway: `Panda.is_grasping` reads pairwise **contact forces** from the last
   physics step (`panda.py:225-253` → `scene.py:821-833`), so `is_cubeA_grasped`
   is False in every hand-injected state, and a grasped probe has to be restored
   from a real rollout's state dict and stepped with the gripper closing. That
   machinery is what was removed.
3. **z-blindness.** A reward measuring only horizontal distance is perfectly
   monotone along z because it is *constant* there, so a monotonicity test passes
   while the reward is blind to the axis stacking happens along. **Nothing
   catches this.**

The mitigation is that `reward.py` is around sixty lines, committed, and read by
eye before it trains anything. That is a weaker claim than the battery made, and
the trade is deliberate: five layers of checking blocked the work that the
checking exists to support.

## 5. Reproducing it

```bash
# 0. the input: a clip of a real failure, from T-II. mp4s are gitignored.
SEEDS=<a seed from t2/results/mode_gap_seed1.csv> WANT=fail bash t2/run.sh videos

# 1. everything
source /workspace/ripl/env.sh
export ANTHROPIC_API_KEY=...          # or $RIPL_ROOT/anthropic.env, chmod 600
MODE=gap VIDEO=~/clip.mp4 bash t3/run.sh all
```

| stage | needs | cost |
|---|---|---|
| `test` | nothing | 1 s |
| `prompt` | ffmpeg | 5 s |
| `generate` | `anthropic`, a key | ~2 min |
| `lint` | nothing | 0.2 s |
| `check` | ManiSkill + the checkpoint | ~10 min |
| `calibrate` | ManiSkill + the checkpoint | ~8 min, optional |
| `summary` | nothing | 1 s |
| `report` | numpy, matplotlib | 5 s |

On the laptop, without a pod: `test`, `prompt`, `generate`, `lint`, `summary`
and `report` all run. See CLAUDE.md's nix-shell note — `ffmpeg` and `anthropic`
(0.109.1 in nixpkgs, which is why the API call uses tool use rather than the
newer structured-output parameter) both come from `nix-shell -p`.

| `test_t3.py` | stdlib | ~1 s, no deps |
| `fixtures/` | data | two positive controls and the stock reward |

`summary.py` is a separate file from `check.py` for one reason: `check.py` must
`import env_t3` at module scope so the forkserver workers register the
environment, which drags ManiSkill in, and the summary has to run on a laptop.
Do not merge them to save a file.

## 7. For the report

- **The prompts** are committed twice on purpose: the editable sources under
  `prompts/` (small, diffable — the thing you tune) and the exact assembled
  `prompt.txt` per run (the thing the model saw — they differ, because the
  contract and the environment source are spliced in). The frames are committed
  beside them.
- **Why the reward would help.** Two arguments, and label them as different
  kinds. *A priori*: the built-in reward is a task-completion reward, uniform
  over the initial-state distribution, and its gradient is flat exactly where the
  base policy is already competent; a mode-targeted reward adds the term the
  failure needs — clearance during the descent for `gap`, settling and release
  quality for `farb`. *Empirical*: the stage ladder and the AUC, against the
  stock reward's on the same episodes. Only the second is evidence.
- **LLM failure modes.** Report which ones the actual generations exhibited and
  which check caught each — and, most interestingly, the near-misses that passed
  the static check and the well-formedness battery and showed up only in the
  alignment numbers. Those are the ones no prompt prevents and only a rollout
  finds. Report the three unchecked classes in §4 as unchecked; a gap you name
  is a finding, a gap you imply is covered is a mistake.
- **Manual effort.** `git log t3/prompts/` is the record: each tuning pass, what
  failed before it and what passed after. Plus generations attempted against
  generations accepted, and the token and wall-clock spend from the manifests.
- **The shape of the harness is itself a finding.** It was built as a five-layer
  gate and cut back to a printed summary, because the gate blocked the work it
  existed to support. That is a real lesson about validating LLM-generated code
  and it belongs in the write-up, not in the commit log.

The debugging narrative goes in `notes/t3-llm-reward.md`, as with T-II.
CLAUDE.md is explicit that those are deliverables, not overhead.
